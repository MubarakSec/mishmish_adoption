## 1. الفكرة العامة وأهداف المشروع
مشروع **مشمش** هو منصة متنقلة لعرض وتبني القطط، مبنية بمعمارية **Client-Server Architecture**:
- **الواجهة الأمامية (Frontend)**: تطبيق هجين مبني بـ **Flutter**، يدعم اللغة العربية بالكامل (RTL)، تصميماً عصرياً، تجربة مستخدم سلسة، وإشعارات نظام حقيقية على الهاتف.
- **الخادم والواجهة الخلفية (Backend)**: خادم متكامل مبني بـ **Laravel (PHP)** يقدم واجهة برمجية RESTful API، يعالج العمليات الحسابية، يدير المصادقة، يفحص المدخلات، ويتحكم بقاعدة البيانات.
- **قاعدة البيانات (Database)**: قاعدة بيانات علائقية **MySQL** لتخزين المستخدمين، القطط، التفضيلات، ورموز الأمان، بما يحقق شرط الدكتورة: *"يمنع استخدام أي بيانات ثابتة داخل فلاتر، كل البيانات تأتي ديناميكياً من MySQL عبر Laravel API"*.

## 2. المعمارية الشاملة وتدفق البيانات (System Architecture)

```
              │  adb reverse tcp:8000     │  (للجهاز الحقيقي عبر USB)
              │  أو 10.0.2.2              │  (لمحاكي أندرويد)
              └─────────────┬─────────────┘
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│              خادم Laravel REST API (Port 8000)           │
│  routes/api.php ──> Middleware (Sanctum) ──> Controllers │
│                           │                             │
│                           ▼                             │
│                     Eloquent ORM                        │
└───────────────────────────┬─────────────────────────────┘
                            │ SQL Queries
                            ▼
┌─────────────────────────────────────────────────────────┐
│                   قاعدة بيانات MySQL                    │
│   users  |  kittens  |  favorites  |  tokens  |  logs   │
└─────────────────────────────────────────────────────────┘
```

### كيف يتواصل الهاتف مع السيرفر المحلي؟
- **على الجهاز الحقيقي (Physical Device عبر USB)**:
  الهاتف الحقيقي يعتبر جهازاً منفصلاً في الشبكة. عندما يطلب `http://127.0.0.1:8000` سيبحث داخل نظام الهاتف نفسه وليس في حاسوبك!
  لذلك نستخدم تقنية **ADB Reverse Port Forwarding**:
  ```bash
  adb reverse tcp:8000 tcp:8000
  ```
  هذا الأمر يخبر نظام أندرويد: *"أي طلب يخرج من الهاتف إلى المنفذ 8000، حوّله عبر كابل الـ USB مباشرة إلى المنفذ 8000 في جهاز المطور"*.
- **على المحاكي (Android Emulator)**:
  محاكي أندرويد يخصص العنوان `10.0.2.2` ليمثل `127.0.0.1` الخاص بجهاز الحاسوب المضيف.
- **التكيف التلقائي في الكود**:
  في ملف [api_service.dart](file:///home/mobta/university/flutter/final_projectV2/mishmish/lib/services/api_service.dart)، يقوم الكود تلقائياً باختبار `127.0.0.1`، وإذا كان التطبيق يعمل داخل محاكي وفشل الاتصال، يتحول فوراً وبشكل صامت إلى `10.0.2.2` دون أن ينهار التطبيق.

## 3. التشريح الهندسي للـ Backend (Laravel & MySQL) - الأساسي

هذا هو القسم الأهم للإجابة على أي سؤال يخص الكود الخلفي:

### أ. هيكلية ملفات الباك إند
داخل مجلد `mishmish-api/`:
- **`routes/api.php`**: سجل المسارات (Routing Registry)؛ يحدد عناوين الـ URL المتاحة للـ API ويربط كل عنوان بالـ Controller المناسب، ويحدد المسارات العامة والمحمية.
- **`app/Http/Controllers/Api/`**:
  - `AuthController.php`: معالجة التسجيل، الدخول، الخروج، إرسال الـ OTP، والتحقق وإعادة التعيين.
  - `KittenController.php`: جلب القطط من قاعدة البيانات وفحص ما إذا كانت مفضلة للمستخدم الحالي.
  - `FavoriteController.php`: عرض مفضلة المستخدم وإضافة/حذف القطط منها (Toggle).
- **`app/Models/`**:
  - `User.php`: نموذج المستخدم، يحتوي على `hasMany(Favorite::class)` وسمات Sanctum و Notifiable.
  - `Kitten.php`: نموذج القط، الحقول القابلة للتعبئة (`$fillable`).
  - `Favorite.php`: جدول الربط، يحتوي على علاقة `belongsTo(User::class)` و `belongsTo(Kitten::class)`.
- **`database/migrations/`**: ملفات بناء جداول MySQL برمجياً.
- **`database/seeders/`**: ملفات زراعة البيانات الأولية النظيفة (`KittenSeeder.php`).
- **`app/Notifications/SendOtpNotification.php`**: إشعار لارفيل الرسمي لإرسال رمز التحقق.
- **`public/images/cats/`**: مجلد وسائط القطط المخدومة محلياً من السيرفر.

### ب. قاعدة البيانات وجداولها والعلاقات (Database Schema & Relations)

يحتوي النظام على **5 جداول رئيسية**:

#### 1. جدول المستخدمين (`users`)
| الحقل | النوع | الوصف |
|:---|:---|:---|
| `id` | BIGINT (PK, Auto-Increment) | المعرف الفريد للمستخدم |
| `name` | VARCHAR(255) | الاسم الكامل |
| `email` | VARCHAR(255) (UNIQUE) | البريد الإلكتروني (غير مكرر) |
| `password` | VARCHAR(255) | كلمة المرور المشفرة بتجزئة Bcrypt |
| `timestamps` | TIMESTAMP | تاريخ الإنشاء والتحديث (`created_at`, `updated_at`) |

#### 2. جدول القطط (`kittens`)
| الحقل | النوع | الوصف |
|:---|:---|:---|
| `id` | BIGINT (PK, Auto-Increment) | معرف القطة |
| `name` | VARCHAR(255) | اسم القطة (مثل: مشمش، توتي، شوكو) |
| `breed` | VARCHAR(255) | السلالة (شيرازي، سيامي، هيمالايا...) |
| `age` | VARCHAR(255) | العمر (مثال: 3 شهور) |
| `description`| TEXT | نبذة وصفية كاملة عن السلوك والشخصية |
| `price` | DECIMAL(8, 2) | رسوم التبني بالريال السعودي |
| `image_url` | VARCHAR(255) | المسار النسبي لصورة القطة في السيرفر (`/images/cats/...`) |

#### 3. جدول المفضلة (`favorites`) - جدول وسيط (Pivot Table)
يربط المستخدمين بالقطط بعلاقة **Many-to-Many**:
| الحقل | النوع | الوصف |
|:---|:---|:---|
| `id` | BIGINT (PK) | المعرف |
| `user_id` | BIGINT (FK -> users.id) | معرف المستخدم صاحب التفضيل (Cascade on delete) |
| `kitten_id`| BIGINT (FK -> kittens.id) | معرف القطة المفضلة (Cascade on delete) |
| `timestamps` | TIMESTAMP | وقت الإضافة للمفضلة |
*ملاحظة أمان وهندسة*: يوجد قيد فريد مركب `UNIQUE(user_id, kitten_id)` يمنع إضافة نفس القطة للمفضلة لنفس المستخدم أكثر من مرة.

#### 4. جدول رموز التحقق واستعادة كلمة المرور (`password_reset_tokens`)
| الحقل | النوع | الوصف |
|:---|:---|:---|
| `email` | VARCHAR(255) (PK) | البريد الإلكتروني للطالب |
| `token` | VARCHAR(255) | رمز الـ OTP المكون من 6 أرقام |
| `created_at` | TIMESTAMP | وقت إنشاء الرمز (يُستخدم للتحقق من انتهاء الصلاحية بعد 15 دقيقة) |

#### 5. جدول توكنات المصادقة (`personal_access_tokens`)
يُدار بواسطة حزمة **Laravel Sanctum**:
يخزن التوكنات المشفرة بصيغة SHA-256، مع تاريخ آخر استخدام، وصلاحيات التوكن (`abilities`).

### ج. دورة حياة الطلب في Laravel (Request Lifecycle)
عندما يرسل تطبيق فلاتر طلباً (مثلاً: تسجيل الدخول `POST /api/login`):
1. **الوصول**: يستقبل خادم الويب (PHP Built-in Server) الطلب ويوجّهه إلى `public/index.php`.
2. **الـ Kernel والتوجيه**: يُمرر الطلب إلى الـ HTTP Kernel، ويتم مطابقته مع المسارات المسجلة في `routes/api.php`.
3. **الـ Middleware**:
   - مسارات المصادقة العامة (مثل التسجيل والدخول) تمر مباشرة.
   - المسارات المحمية (مثل المفضلة وتسجيل الخروج) تمر عبر `auth:sanctum`. يقوم الـ Middleware باستخراج التوكن من الـ Header:  
     `Authorization: Bearer <token>`  
     ويبحث عنه في جدول `personal_access_tokens`. إذا وُجد وكان صالحاً، يربط المستخدم بالطلب `$request->user()`. وإذا لم يوجد، يرفض الطلب فوراً بكود `401 Unauthorized`.
4. **الـ Controller والـ Validation**:
   يستقبل الميثود المناسب في الـ Controller كائن الـ `Request`، ويطبق دوال التحقق `validate()`.
5. **التعامل مع قاعدة البيانات (Eloquent ORM)**:
   يتواصل الموديل مع MySQL لتنفيذ الاستعلام المطلوب.
6. **الرد (Response)**:
   يُرجع الـ Controller كائن `response()->json([...], statusCode)` بصيغة JSON القياسية مع ترويسات `Content-Type: application/json`.

### د. نظام التوثيق والحماية (Sanctum & Bcrypt Security)

#### 1. لماذا Sanctum؟
Laravel Sanctum هي الحزمة القياسية الخفيفة المخصصة للـ Single Page Applications (SPAs) وتطبيقات الموبايل (Mobile APIs). على عكس Passport المعقد الذي يتطلب خادم OAuth2 كامل مع مفاتيح تشفير ثقيلة، يولد Sanctum توكنات نصية بسيطة (Personal Access Tokens) عالية الأداء وعالية الأمان.

#### 2. توليد التوكن:
عند التسجيل أو تسجيل الدخول بنجاح:
```php
$token = $user->createToken('auth-token')->plainTextToken;
```
- لارفيل يقوم بتشفير التوكن وتخزينه في جدول `personal_access_tokens`.
- يرجع الـ `plainTextToken` مرة واحدة فقط إلى تطبيق فلاتر.
- فلاتر يحفظه محلياً في `SharedPreferences`، ويرسله في ترويسة كل طلب محمي:
  ```
  Authorization: Bearer 1|xxxxxxxxxxxxxxxxxxxxxxxxxxxx
  ```

#### 3. تشفير كلمات المرور (Password Hashing):
لا يتم إطلاقاً تخزين كلمة المرور كنص صريح!
```php
'password' => Hash::make($validated['password'])
```
لارفيل يستخدم خوارزمية **Bcrypt** ذات التمليح التلقائي (Salted Hashing) بمعدل أمان عالي، مما يجعل استرجاع كلمة المرور الأصلية مستحيلاً رياضياً حتى لو سُرقت قاعدة البيانات.
وعند تسجيل الدخول، يتم التحقق منها عبر:
```php
if (!Hash::check($password, $user->password)) {
    return response()->json(['message' => 'بيانات الدخول غير صحيحة'], 401);
}
```

#### 4. إبطال التوكن عند الخروج (Logout):
```php
$request->user()->currentAccessToken()->delete();
```
هذا السطر يحذف التوكن الحالي فقط من جدول `personal_access_tokens`. وبذلك، إذا حاول أي شخص استخدام نفس التوكن لاحقاً، سيرفضه السيرفر فوراً.

### هـ. نظام التحقق من البيانات (Request Validation)
في جميع شاشات الدخول والتسجيل والاستعادة، لا يعتمد السيرفر أبداً على فحص الفرونت إند (لأن الفرونت إند يمكن تجاوزه بـ Postman أو Curl). يقوم الباك إند بالتحقق الصارم:
- **في التسجيل (`register`)**:
  ```php
  $request->validate([
      'name' => 'required|string|max:255',
      'email' => 'required|email|unique:users',
      'password' => 'required|string|min:6|confirmed',
  ]);
  ```
  - `unique:users`: يفحص تلقائياً جدول المستخدمين للتأكد من عدم وجود الإيميل مسبقاً لمنع التكرار.
  - `confirmed`: يشترط وجود حقل اسمه `password_confirmation` مطابق تماماً لكلمة المرور.
  - `min:6`: يمنع كلمات المرور الضعيفة الأقل من 6 خانات.
- **إذا فشل التحقق**:
  يرد لارفيل تلقائياً بكود **`422 Unprocessable Content`** ومصفوفة بأسماء الحقول التي بها خطأ ورسائل الخطأ التفصيلية، والتي يقوم تطبيق فلاتر بقراءتها وعرضها للمستخدم بشكل لائق.

### و. نظام استعادة الحساب ورمز التحقق (OTP & Laravel Notifications)

هذه الميزة مطبقة بأعلى المعايير الأمنية وبمطابقة حرفية لمتطلبات د. دينا:

#### التدفق الأمني للـ OTP:
1. **الطلب (`POST /api/forgot-password`)**:
   - يتحقق السيرفر من وجود البريد في جدول `users`.
   - يولد كود تحقق عشوائي آمن مكون من 6 أرقام:
     ```php
     $code = sprintf('%06d', mt_rand(100000, 999999));
     ```
   - يحفظه أو يحدّثه في جدول `password_reset_tokens` مع توثيق الوقت الحالي:
     ```php
     DB::table('password_reset_tokens')->updateOrInsert(
         ['email' => $request->email],
         ['token' => $code, 'created_at' => now()]
     );
     ```
   - يُرسل الإشعار عبر فئة **Laravel Notification الرسمية**:
     ```php
     $user->notify(new SendOtpNotification($code));
     ```
     ويتم توثيقه في سجلات النظام `storage/logs/laravel.log` ليكون بمثابة إثبات جاهز للدكتورة أثناء التقييم، بالإضافة لإرجاع الرمز في الـ JSON ليقوم تطبيق فلاتر بإسقاط إشعار نظام حقيقي على هاتف أندرويد.

2. **التحقق من الكود (`POST /api/verify-code`)**:
   - يتأكد السيرفر من مطابقة الإيميل مع الرمز المدخل.
   - **فحص انتهاء الصلاحية**: يتحقق السيرفر برمجياً عبر مكتبة Carbon أن الرمز لم يمر عليه أكثر من 15 دقيقة:
     ```php
     if (\Carbon\Carbon::parse($record->created_at)->addMinutes(15)->isPast()) {
         return response()->json(['message' => 'انتهت صلاحية رمز التحقق'], 422);
     }
     ```

3. **إعادة التعيين الآمنة (`POST /api/reset-password`)**:
   - **سد الثغرة الأمنية**: لا يسمح السيرفر بتغيير كلمة المرور بمجرد معرفة الإيميل! بل يشترط إعادة إرسال الكود (`code`) في الطلب، ويعيد فحصه والتأكد من صلاحيته قبل أي تعديل.
   - يتم تحديث كلمة المرور مشفرة:
     ```php
     $user->update(['password' => Hash::make($request->password)]);
     ```
   - يتم **حذف الكود فوراً** من جدول `password_reset_tokens` لضمان عدم إعادة استخدامه مرة ثانية نهائياً (Single-Use Token).

## 4. مرجع مسارات الـ API بالكامل (API Endpoints Reference)

| الميثود | المسار (URI) | الحماية (Auth) | معلمات الإدخال (Request Body) | الاستجابة الناجحة (Success Response) | كود الحالة |
|:---:|:---|:---:|:---|:---|:---:|
| `POST` | `/api/register` | عام | `name`, `email`, `password`, `password_confirmation` | `user`, `token`, `message` | `201 Created` |
| `POST` | `/api/login` | عام | `email` (أو username), `password` | `user`, `token`, `message` | `200 OK` |
| `POST` | `/api/forgot-password` | عام | `email` | `message`, `code` | `200 OK` |
| `POST` | `/api/verify-code` | عام | `email`, `code` | `message` | `200 OK` |
| `POST` | `/api/reset-password` | عام | `email`, `code`, `password`, `password_confirmation` | `message` | `200 OK` |
| `GET` | `/api/kittens` | عام (يكتشف التوكن إن وُجد) | لا يوجد | قائمة كاملة بجميع القطط مع حقل `is_favorite` | `200 OK` |
| `GET` | `/api/kittens/{id}` | عام (يكتشف التوكن إن وُجد) | `id` في الرابط | تفاصيل القطة مع حقل `is_favorite` | `200 OK` |
| `POST` | `/api/logout` | محمي (`auth:sanctum`) | لا يوجد | `message` (تم حذف التوكن من السيرفر) | `200 OK` |
| `GET` | `/api/favorites` | محمي (`auth:sanctum`) | لا يوجد | قائمة بالقطط المفضلة للمستخدم الحالي | `200 OK` |
| `POST` | `/api/favorites/{kittenId}` | محمي (`auth:sanctum`) | `kittenId` في الرابط | `is_favorite: bool`, `message` | `200 OK` |

## 5. تشريح الفرونت إند (Flutter Architecture)

### أ. إدارة الاتصال والشبكة (`ApiService`)
ملف [api_service.dart](file:///home/mobta/university/flutter/final_projectV2/mishmish/lib/services/api_service.dart) يمثل بوابة الاتصال الموحدة (Singleton Service):
- يجهز الترويسات القياسية تلقائياً:
  ```dart
  'Content-Type': 'application/json',
  'Accept': 'application/json',
  if (token != null) 'Authorization': 'Bearer $token',
  ```
- **معالجة الأخطاء الذكية (`_handleResponse`)**:
  إذا حدث خطأ من السيرفر، يفحص ما إذا كانت الاستجابة JSON ويستخرج الخطأ العربي الواضح من مصفوفة `errors` أو حقل `message`. وإذا حدث خطأ غير متوقع في الخادم (كود 500)، يعرض رسالة مهذبة بدلاً من إظهار استثناء تقني (Crash).

### ب. إدارة الحالة والتخزين المحلي (`SharedPreferences`)
نستخدم الحزمة الإلزامية `shared_preferences` لتخزين 4 مفاتيح خفيفة:
1. `auth_token`: التوكن السري للمصادقة؛ وجوده يعني أن المستخدم مسجل دخول بالفعل.
2. `onboarding_done`: قيمة Boolean تحدد هل شاهد المستخدم شاشات الـ Onboarding سابقاً أم لا.
3. `user_name` و `user_email`: لعرضها فوراً في شاشة الحساب (Profile) دون انتظار استعلام شبكة.

#### المنطق الذكي لشاشة البداية (`SplashScreen`):
عند فتح التطبيق، تنتظر الشاشة ثانيتين ثم تقرأ القيم المخزنة محلياً:
- إذا كان `onboarding_done == false` ⬅️ يفتح شاشة **التعريف (Onboarding)** لأول مرة فقط.
- إذا كان `onboarding_done == true` ولكن `auth_token == null` ⬅️ يفتح شاشة **تسجيل الدخول (Login)**.
- إذا كان `auth_token != null` ⬅️ يفتح مباشرة الشاشة **الرئيسية (Home)**.
*هذا يحقق متطلب د. دينا حرفياً وبدقة متناهية.*

### ج. التزامن اللحظي للمفضلة (Optimistic UI & Live Heart Sync)
- عند فتح الصفحة الرئيسية، كل بطاقة قطة تحتوي على زر قلب تفاعلي.
- عند النقر على القلب:
  1. يتغير لون القلب فوراً إلى الأحمر أو الرمادي على الواجهة بلحظتها (Optimistic Update) لتجربة استخدام فائقة السرعة بدون تأخير.
  2. يتم إرسال طلب `POST /api/favorites/{id}` بالخلفية إلى لارفيل لتعديل جدول `favorites` في MySQL.
  3. إذا فشل الاتصال لسبب ما، يعود القلب تلقائياً لحالته السابقة ويظهر تنبيه للمستخدم.
- شاشة التفاصيل [kitten_detail_screen.dart](file:///home/mobta/university/flutter/final_projectV2/mishmish/lib/screens/home/kitten_detail_screen.dart) تبدأ بحالة `_isFavorite = widget.kitten.isFavorite` الفعلية القادمة من قاعدة البيانات لضمان عدم وجود أي تناقض بين الشاشات.

### د. نظام الإشعارات المحلي على الهاتف (System Notifications)
باستخدام `flutter_local_notifications`:
- عند طلب استعادة كلمة المرور، يرجع كود الـ OTP من الـ API، وتستدعي الدالة:
  ```dart
  NotificationService.showOtpNotification(code);
  ```
- تقوم الدالة بإنشاء قناة نظام أندرويد رسمية (`otp_channel`) بأعلى درجات الأهمية (`Importance.max`) وأعلى أولوية (`Priority.high`)، مع تفعيل الاهتزاز والصوت.
- يهبط إشعار من شريط الإشعارات العلوي على الهاتف الفعلي حاملاً رمز التحقق، دون الحاجة لأي نوافذ SnackBar مزعجة.

## 6. بنك الأسئلة المتوقعة من الدكتورة مع الإجابات النموذجية (Defense Cheat Sheet)

استخدم هذه الإجابات النموذجية أثناء المناقشة لإبهار اللجنة:

#### س1: لماذا اعتمدتم على Laravel Sanctum بدلاً من الجلسات (Sessions) أو حزمة Passport؟
> **الإجابة النموذجية**:  
> "لأن تطبيقات الموبايل بطبيعتها Stateless (لا تدعم الكوكيز التقليدية للويب مثل المتصفحات). حزمة Sanctum توفر نظام مصادقة Token-based خفيف وسريع، حيث يُرسل التوكن في ترويسة `Authorization: Bearer` مع كل طلب، وهو أسرع وأخف بكثير من حزمة Passport التي تتطلب خادم OAuth2 معقد لا تحتاجه تطبيقات الهاتف الفردية."

#### س2: كيف يضمن النظام عدم استخدام أي بيانات ثابتة داخل تطبيق فلاتر كما هو مطلوب في المشروع؟
> **الإجابة النموذجية**:  
> "جميع بيانات القطط (الأسماء، السلالات، الأعمار، الأسعار، الأوصاف، ومسارات الصور) مخزنة في جدول `kittens` داخل MySQL، ويتم جلبها عبر `GET /api/kittens`. حتى روابط الصور لا يتم تثبيتها في فلاتر بل تأتي من السيرفر كمسار نسبي يتم تركيبه ديناميكياً مع الـ Base URL، وتطبيق فلاتر يحتوي فقط على كود عرض الواجهات و Model لتحويل استجابة JSON إلى كائنات Dart."

#### س3: كيف حميتم مسار إعادة تعيين كلمة المرور (`reset-password`) من الثغرات الأمنية؟
> **الإجابة النموذجية**:  
> "قفلنا الثغرة الشائعة في مشاريع الطلاب؛ مسار `reset-password` لا يقبل فقط الإيميل والباسورد، بل يشترط تمرير رمز الـ OTP الذي تم التحقق منه. يتحقق السيرفر أولاً من وجود الرمز ومطابقته في جدول `password_reset_tokens`، ويتأكد أن تاريخ إنشائه لم يتجاوز 15 دقيقة عبر Carbon. وفور التعيين الناجح، يتم حذف الرمز فوراً من قاعدة البيانات لضمان عدم استخدامه مرة ثانية نهائياً (One-Time Token)."

#### س4: كيف تم التعامل مع مشكلة الوصول للباك إند المحلي (`localhost:8000`) من الهاتف الحقيقي؟
> **الإجابة النموذجية**:  
> "الهاتف الحقيقي يعتبر شبكة مستقلة ولا يرى `127.0.0.1` الخاص بالكمبيوتر. لحل هذه المشكلة هندسياً بدون الحاجة لتغيير الـ IP في كل شبكة Wi-Fi، استخدمنا تقنية `adb reverse tcp:8000 tcp:8000`، التي تحول كل طلبات المنفذ 8000 من كابل الـ USB مباشرة إلى حاسوب التطوير، وتم أتمتة هذه الخطوة داخل سكربت `run.sh` لتعمل تلقائياً فور توصيل الجهاز."

#### س5: كيف تعمل مزامنة المفضلة بين شاشتي الرئيسية والمفضلة؟
> **الإجابة النموذجية**:  
> "عندما يطلب المستخدم قائمة القطط `GET /api/kittens` وهو مسجل دخول، يتعرف السيرفر على المستخدم عبر توكن Sanctum، ويفحص القطط التي أضافها المستخدم في جدول `favorites`، ويرجع مع كل قط حقل Boolean اسمه `is_favorite`. بناءً عليه، يظهر القلب ملوناً في الرئيسية والتفاصيل تلقائياً، وأي إضافة أو حذف تستدعي مسار `toggle` الذي يضيف السجل أو يحذفه ويعيد الحالة الجديدة."

#### س6: أين يتم حفظ إشعار الـ OTP وكيف أثبت للدكتورة أنه تم عبر Laravel Notifications؟
> **الإجابة النموذجية**:  
> "يوجد لدينا فئة إشعار مخصصة في الباك إند هي `App\Notifications\SendOtpNotification`. عند طلب الرمز، يقوم السيرفر باستدعاء `$user->notify(new SendOtpNotification($code))`. وللتوثيق والإثبات، يتم تسجيل هذا الإشعار تلقائياً في ملف سجلات لارفيل `storage/logs/laravel.log`، حيث يمكننا فتحه أمام الدكتورة ورؤية الإشعار والوقت والكود المسجل نصياً."

#### س7: ماذا يحدث إذا انقطع الاتصال أو توقف السيرفر مؤقتاً؟
> **الإجابة النموذجية**:  
> "الكود محمي بطبقات حماية متينة (Fail-Safe):
> 1. الـ `ApiService` محاط بـ `try-catch` ومهلة انتظار Timeout مدتها 4 ثوانٍ تمنع تعليق الشاشة، وتظهر واجهة إعادة محاولة ودية ومريحة للمستخدم بدلاً من الكراش.
> 2. عارض الصور في فلاتر مزود بـ `errorBuilder` ذكي؛ فإذا تعذر جلب الصورة من شبكة السيرفر، يعرض فوراً وبشكل صامت النسخة الاحتياطية المطابقة لها من مجلد الـ Assets المحلي حتى لا تظهر أي بطاقة مكسورة."
